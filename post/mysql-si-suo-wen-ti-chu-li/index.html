mysql死锁问题处理

2026-06-04 9 min read
  1. 死锁的本质

两个或多个事务互相持有对方需要的锁，形成环路等待，永远无法完成。

事务 A 事务 B
──────── ────────
BEGIN; BEGIN;
UPDATE t SET val=1 WHERE id=1; UPDATE t SET val=2 WHERE id=2;
→ 拿到 id=1 的行锁 ✅ → 拿到 id=2 的行锁 ✅

UPDATE t SET val=1 WHERE id=2; UPDATE t SET val=2 WHERE id=1;
→ 等待 id=2 的锁 ⏳ → 等待 id=1 的锁 ⏳
→ 死锁！MySQL 回滚其中一个 💥

2.2 实时锁监控（MySQL 8.0）

-- 当前持有的锁
SELECT * FROM performance_schema.data_locks;

-- 当前锁等待

-- 详细锁等待视图（推荐）
SELECT
r.trx_id AS waiting_trx_id,
r.trx_mysql_thread_id AS waiting_thread,
r.trx_query AS waiting_query,
b.trx_id AS blocking_trx_id,
b.trx_mysql_thread_id AS blocking_thread,
b.trx_query AS blocking_query,
b.trx_started AS blocking_started
FROM information_schema.innodb_lock_waits w
JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_trx_id
JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_trx_id;

-- MySQL 8.0+ 推荐用 sys 库
SELECT * FROM sys.innodb_lock_waits\G

  1. 常见死锁场景与解决

3.1 场景一：不同顺序更新多行

-- ❌ 事务 A: 先锁 1 再锁 2
-- ❌ 事务 B: 先锁 2 再锁 1

-- ✅ 解决：统一按主键升序加锁
-- 两个事务都按 id 从小到大的顺序更新
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

3.2 场景二：INSERT → 唯一索引冲突

-- 两个事务同时 INSERT 同一个唯一键值
-- 各自持有 gap lock / insert intention lock，互相等待

-- ❌ 事务 A: INSERT INTO t (uniq_col) VALUES (100);
-- ❌ 事务 B: INSERT INTO t (uniq_col) VALUES (100);

-- ✅ 解决方案：
-- 方案 1：INSERT IGNORE（冲突时忽略）
INSERT IGNORE INTO t (uniq_col) VALUES (100);

-- 方案 2：ON DUPLICATE KEY UPDATE
INSERT INTO t (uniq_col, val) VALUES (100, 'a')
ON DUPLICATE KEY UPDATE val = VALUES(val);

-- 方案 3：REPLACE INTO（先删后插，慎用）
REPLACE INTO t (uniq_col, val) VALUES (100, 'a');

-- 方案 4：应用层先查再插（减少冲突概率）
SELECT id FROM t WHERE uniq_col = 100 FOR UPDATE;
-- 如果不存在再 INSERT

3.3 场景三：Gap Lock 范围重叠

-- RR 隔离级别下，范围查询会产生 Gap Lock
-- 两个事务的范围重叠时可能死锁

-- ❌ 事务 A:
SELECT * FROM orders WHERE customer_id BETWEEN 10 AND 20 FOR UPDATE;
-- ❌ 事务 B:
SELECT * FROM orders WHERE customer_id BETWEEN 15 AND 25 FOR UPDATE;

-- ✅ 解决方案：
-- 方案 1：降低隔离级别为 READ COMMITTED
SET SESSION transaction_isolation = 'READ-COMMITTED';
-- RC 下没有 Gap Lock

-- 方案 2：缩小范围，减少重叠

-- 方案 3：用精确条件替代范围
-- 改为：
SELECT * FROM orders WHERE customer_id = 15 FOR UPDATE;

3.4 场景四：事务内混合使用不同索引

-- 表有两个索引：idx_a(a), idx_b(b)
-- ❌ 事务 A: UPDATE t SET b = 1 WHERE a = 10; -- 锁 idx_a
-- ❌ 事务 B: UPDATE t SET a = 1 WHERE b = 10; -- 锁 idx_b
-- 然后各自需要对方的锁 → 死锁

-- ✅ 解决方案：
-- 用主键统一加锁
SELECT id FROM t WHERE a = 10 FOR UPDATE; -- 先拿到所有行的主键锁
UPDATE t SET b = 1 WHERE id IN (...); -- 再更新

3.5 场景五：大事务 + 长时间持有锁

-- ❌ 事务里做了太多操作（查询、计算、外部 API 调用、再更新）
BEGIN;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
-- ... 调用了外部支付接口（耗时 5 秒）...
UPDATE orders SET status = 'paid' WHERE id = 1;
COMMIT;

-- ✅ 解决方案：
-- 1. 把读和写分开，减少锁持有时间
-- 2. 先完成外部调用，最后再开事务更新
-- 3. 必须锁的话，设置锁等待超时
SET innodb_lock_wait_timeout = 3; -- 等 3 秒就放弃

  1. 死锁预防策略

4.1 统一加锁顺序

-- 所有事务按相同顺序操作表和行
-- 推荐：按主键 ASC 顺序

-- ✅ 批量更新时排序
UPDATE accounts SET balance = balance - 100 WHERE id IN (3, 1, 2);
-- 改为
UPDATE accounts SET balance = balance - 100 WHERE id IN (1, 2, 3);

4.2 减小事务粒度

-- ❌ 大事务
BEGIN;
UPDATE t SET a = 1 WHERE id = 1;
-- ... 很多其他操作 ...
UPDATE t SET b = 2 WHERE id = 2;
COMMIT;

-- ✅ 拆成小事务
BEGIN; UPDATE t SET a = 1 WHERE id = 1; COMMIT;
BEGIN; UPDATE t SET b = 2 WHERE id = 2; COMMIT;

4.3 使用乐观锁替代悲观锁

-- ❌ 悲观锁：SELECT ... FOR UPDATE（长时间持锁）
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 业务计算...
UPDATE accounts SET balance = 500 WHERE id = 1;
COMMIT;

-- ✅ 乐观锁：用版本号检测冲突
-- 表结构加 version 字段
ALTER TABLE accounts ADD COLUMN version INT DEFAULT 0;

-- 读取
SELECT balance, version FROM accounts WHERE id = 1;
-- 假设读到 version = 5, balance = 600

-- 更新（CAS）
UPDATE accounts
SET balance = 500, version = version + 1
WHERE id = 1 AND version = 5;
-- 检查 affected rows，如果是 0 说明被别人改了，重试

4.4 合理设置隔离级别

-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- READ COMMITTED：无 Gap Lock，减少死锁概率
SET SESSION transaction_isolation = 'READ-COMMITTED';

-- 权衡：RC 下可能出现不可重复读和幻读
-- 适合：读多写少、能接受短暂不一致的场景

4.5 锁等待超时

-- 不无限等锁，超时就放弃（应用层重试）
SET SESSION innodb_lock_wait_timeout = 5; -- 默认 50 秒太长了

-- 应用层捕获错误码重试
-- MySQL Error 1213 = Deadlock
-- MySQL Error 1205 = Lock wait timeout

try:

  1. 诊断 Checklist

遇到死锁时，按以下顺序排查：

□ 1. SHOW ENGINE INNODB STATUS\G
→ 获取死锁涉及的表、索引、SQL

□ 2. 确认死锁类型
□ 同表不同行顺序？→ 统一加锁顺序
□ 不同表交叉加锁？→ 统一表操作顺序
□ 唯一索引冲突？→ INSERT IGNORE / ON DUPLICATE KEY
□ Gap Lock 重叠？→ 降级为 RC / 缩小范围
□ 混合索引？→ 统一用主键加锁

□ 3. 检查事务设计
□ 事务是否太大？→ 拆分
□ 锁持有时间是否太长？→ 外部操作移到事务外
□ 是否可以用乐观锁？

□ 4. 配置检查
□ innodb_lock_wait_timeout 是否合理？
□ innodb_print_all_deadlocks 是否开启？
□ 隔离级别是否合适？

□ 5. 应用层
□ 是否有死锁重试机制？
□ 是否有退避策略（避免反复碰撞）？
